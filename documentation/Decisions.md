## 2. Project overview

The team will develop a standalone C++ desktop application that gradually evolves into a POS system for a small retail store. Each increment will build on the previous application.

Increment 1 focuses on barcode generation and reading. The graded in-class demonstration is scheduled for **November 12, 2026**. Later increments are expected approximately weekly, but their exact schedule and requirements have not been formally established.

The long-term objective is a functioning retail POS application. Future functionality will be determined as further requirements are provided.

## 3. Increment 1: Barcode system

### 3.1 Barcode generation

1. The user opens the desktop application and selects barcode generation.
2. The user enters a six-digit numeric code.
3. The application validates the input and displays an appropriate error if it is invalid.
4. For valid input, the team-written encoder produces a Code 128 Set B pattern.
5. Qt draws and saves the barcode image, and the application displays it.

The input must contain **exactly six digits and start with a non-zero digit**, as required by the assignment. It can be stored as a string so its characters can be validated individually.

Valid examples: `100000`, `123456`, `999999`.

Invalid examples:

- Empty input — no code supplied
- `12345` — fewer than six digits
- `1234567` — more than six digits
- `123A56` — contains a non-numeric character
- `000001` or `004281` — starts with zero

The six-digit restriction is an application requirement, not an inherent limitation of Code 128.

### 3.2 Barcode reading

The team will support both reading methods:

**Image upload**

1. The user selects barcode reading and chooses an image.
2. OpenCV loads and processes the selected image.
3. The team's decoder attempts to read the barcode.
4. The application displays the decoded information or an appropriate error.

**Camera scanning**

1. The user selects barcode reading and camera scanning.
2. OpenCV accesses the camera and provides frames for processing.
3. The team's decoder attempts to read the barcode from a frame.
4. The application displays the result when a barcode is recognized.

The reader needs to support the Code 128 barcodes generated by this application and display the original six-digit code. When multiple barcodes are detected, the application asks the user to scan one at a time. Supporting both methods is a team decision; the assignment says the barcode can be uploaded as an image **or** scanned through the laptop camera.

### 3.3 Error handling

The application should communicate problems clearly, including empty input, incorrect length, non-numeric input, a leading zero, unreadable image files, images without recognizable barcodes, decoding failures, unavailable cameras, and image-saving failures.

## 4. Technical decisions

### DEC-001: Programming language — C++

C++ is required by the assignment. Application logic, barcode generation, and integration components will be developed in C++.

### DEC-002: Development model — Incremental

Each increment will extend the existing application as additional requirements become available.

### DEC-003: Barcode format — Code 128

The application will generate Code 128 barcodes. The format supports numeric data and can represent the six-digit input directly.

### DEC-004: Custom barcode encoding

The team will implement barcode encoding in its own C++ code. As clarified to the team, non-standard libraries cannot be used for barcode encoding or decoding; libraries for image processing and file handling are allowed.

The encoder must address input validation, Code 128 symbol representation, start and stop patterns, checksum calculation, and conversion into a barcode pattern. Qt will draw and save the image from that pattern. The encoder's internal design will be established during component design.

### DEC-005: Custom barcode decoding

The team will implement decoding in C++. ZXing-C++ is not permitted for decoding or encoding. The decoder will read the application's generated Code 128 barcodes, recover the original six digits, and validate the barcode. The earlier plan to use ZXing-C++ and support all of its formats is superseded.

### DEC-006: Desktop framework — Qt

Qt will be used for barcode image rendering and saving. A simple interface is acceptable; an elaborate graphical frontend is not required. The application must still display the generated barcode.

OpenCV will be used for reading-side image and camera handling. The team-written encoder and decoder are responsible for translating between digits and Code 128 patterns.

### DEC-018: Generated barcode images — Qt

Qt draws and saves barcode images from the pattern produced by the team's encoder. OpenCV is used separately for reading-side image and camera handling.

### DEC-019: Reading responsibilities

Person 4 will handle uploaded images and camera frames using OpenCV, and prepare barcode candidates for Person 5. Person 5 will implement Code 128 decoding and return whether a barcode was decoded, a message, and the code. Person 2's Code 128 patterns and checksum logic can be shared with the decoder. The exact interfaces are described in the implementation plan and require integration testing.

Whether OpenCV's barcode-specific detection-only function is permitted has not been confirmed. General image processing is allowed; team-written locating logic is the fallback if barcode-specific detection is prohibited.

## 5. Architecture and design workflow

### 5.1 Initial planning

The team has held a kickoff meeting covering the project objective, increment 1 workflows, technical dependencies, responsibilities, and documentation.

### 5.2 High-level design

The project will be divided into functional components with assigned responsibilities and clear boundaries.

### 5.3 Individual low-level design

Each member will prepare a design for their assigned component, considering classes, data structures, functions, inputs and outputs, dependencies, error handling, and interactions. The team allocated an initial one-day planning period.

### 5.4 Compatibility review

The team will review component designs together for dependencies, incompatible assumptions, overlapping responsibilities, missing functionality, data exchange, and interface inconsistencies. AI-assisted analysis may support this review; final architectural decisions remain the team's responsibility.

### 5.5 Consolidated design and UML

Following the review, the team will reconcile individual designs into an agreed system design covering responsibilities, shared interfaces, class relationships, dependencies, and data flow. UML diagrams will document the consolidated design and be updated when significant changes are approved.

## 6. Documentation strategy

Collaborative project documentation will be tracked in Git and accessible to the team.

### Raw meeting documentation

Meeting notes will preserve historical discussion, including topics, proposals, alternatives, problems, questions, opinions, decisions, and action items. Raw notes do not automatically represent approved technical decisions and should not be rewritten to erase historical discussions.

### Consolidated documentation

Consolidated documents will describe current approved requirements, designs, and implementation. They may include architecture, component documentation, UML diagrams, interface specifications, implementation explanations, and decision records. Approved approaches should be identifiable when alternatives have been discussed.

### Decision records

Significant decisions should record the context, selected approach, rationale, relevant alternatives, and implications, so future team members can understand the reasoning.

### Technical documentation

Documentation should explain important details that are difficult to infer from code. For example, the custom Code 128 encoder should explain its input representation, encoding process, checksum, resulting pattern, and important design decisions or limitations. Prioritize clarity and maintainability over describing every trivial line.
